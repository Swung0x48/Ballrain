# 段搜索（segment search，“自动 TAS”）

`ballrain/segsearch/`：在 TAS 路线上两个门 A、B 之间，从 TAS 在 A 的状态出发，用真实的 headless 引擎搜按键序列，
找比 TAS 更早到 B、并且到 B 时状态不明显变差的线。每条报告出来的线都从冷启动重放一遍，逐位一致才算数。

为什么要它：RL 学的是平均回报，只“有时成功”的快线会被它放弃；搜索只要有一条成功的就留下。所以它回答“这一段有没有比
TAS 更快的走法、快多少”，找到的线还可以当训练示范。

## 用法

```powershell
python -m ballrain.segsearch search --a 18653 --b 23300 --out runtime/segsearch/s4-cp4-slope --workers 7 --seed 1
python -m ballrain.segsearch plot runtime/segsearch/s4-cp4-slope/result.json --title "小节4 盘点 → 坡顶"
python -m ballrain.segsearch rollouts runtime/segsearch/s4-cp4-slope --title "小节4 盘点 → 坡顶"
```

输出（都在 `--out` 下，`runtime/` 不进 git）：`result.json`（门、TAS 参考、统计、验证过的线：A→B 的按键 run 列表、帧数、
SR 毫秒、和 TAS 的差、终点检查、整条位置）、`search.log`、`view.png`（全关俯视 + 这一段俯视 + 沿 TAS 线的侧视）、`rollouts.npz`（试过的每条 rollout 自己新走的
部分：位置、帧、父分支、怎么结束、按键来源、因少吃球被丢的门）和 `rollouts` 子命令画的 `rollouts.png`（按结局分面板的
俯视 + 高度随时间）。
`result.json` 只存 A→B 这一段的按键和数据集 framelog 的 sha256，不存 TAS 前缀。

默认数据集是 `runtime/datasets/tas-v1/HS01_4740_1_30_344`（`run/framelog.bin` = 纪录实际执行的帧）。引擎：
`runtime/hl-win/bin-x86p2002f-pressure/BallanceMMOSimTool.exe`，根目录 `runtime/hl-win/game`
（环境变量 `BALLRAIN_SEG_BIN` / `BALLRAIN_SEG_ROOT` 可改）。副本标签 hl-40..hl-47，`--workers` 最多 8。
每个 worker 把自己启动过的引擎 PID 记在 `<out>/work/pids-hl-4N.txt`；每个进程用完就由它自己的句柄结束（PID 会被别的进程重用，查“还活着的是不是我的”要看进程树：引擎的父进程是 pool worker，祖父进程的命令行含 `ballrain.segsearch`）。

测试：`python -m pytest tests/test_segsearch.py`（不需要引擎）；`BALLRAIN_SEG_ENGINE_TEST=1` 时再跑一个引擎测试
（TAS 原样重放 + 分块不变性，hl-47）。

## 设计（选了什么、为什么）

**状态恢复 = 引擎自己的前缀重放。** agent 协议没有存档 / 读档（`ballrain_agent.cpp` 只 include 了 BMMO 的
physics savestate 头文件，没接到协议上）。所以一个分支 = 一个新进程：`BALLRAIN_PREFIX` = TAS[:A] + 这个分支到目前为止的
按键，引擎不发观测地重放（实测约 13k 帧/秒）；之后才一块一块发新按键、每块收一个观测。实测（这台 14700KF，单进程）：

| 项 | 数 |
|---|---|
| 启动 + 前缀到 TAS 帧 18653 | 1.65–1.85 s |
| 启动 + 前缀到 TAS 帧 936 | 0.47 s |
| 1 帧一块步进 | ~2.5k 帧/s |
| 2 帧一块 | ~4k 帧/s |
| 8 帧一块 | ~11k 帧/s |

一次 rollout 的引擎时间约 86% 花在恢复上，所以搜索的设计是：每次恢复后让 rollout 一直跑下去（直到 B、死球或落后太多），
沿途过的每个子门都留一个分支——一次恢复换来很多分支。

**分块不变性（先测过）：** 同一串非 TAS 按键用 1 帧块、2 帧块、8 帧块、一整块、以及写进前缀重放，所有观测帧的位置和
速度逐位相同。这是“搜索里看到的 = 冷启动重放看到的”的前提。

**球序固定为 `ckid`。** 不带种子的 `retail` 每个进程抽一个新球序，run 不能重复。`ckid` 下 headless 重放 4740 TAS
在两段里与数据集记录的位置偏差为 0。结果都标“headless，ckid”；零售 Player.exe 才是权威，这里没有在零售上验证。

**门。** A 是 TAS 帧（交接点）。A 和 B 之间每 `--gate-every` 个 TAS 帧（默认 264 = 1 秒游戏时间）一个子门，B 是最后一个门。
门是过 TAS 在该帧位置、法向沿 TAS 速度的平面；轨迹从负侧穿到非负侧、且穿过点离 TAS 点不超过 `--radius`（默认 6）才算过门。
过门时间在两个观测之间线性插值（排序用）；冷启动验证用 1 帧块，给出整数帧和 SR。TAS 自己的门时间用同一个检测器、
在同一个引擎上量（参考 run），所以“比 TAS 快”是同引擎同检测器的比较。

**搜索 = 分阶段 beam。** 第 g 阶段从过了门 g 的分支里选 `--k` 个：先选至多 `--k-surv` 个“活下来的”（造出它的那次 rollout 又往前过了至少 `--ahead` 个门）里最早的，再按时间补满（位置和速度都相差 < 0.25 的算重复，跳过）；再加
`--k-speed` 个在最早者 `--slack` 帧内速度最大的。每个分支做 `--m` 次 rollout（之前展开过的减半）：按键 = TAS 从它自己过门 g
的那一帧起的按键（按门对齐，不按帧号——分支领先了，TAS 后面的按键要从相同路程处接上），然后：

- 第一个 rollout 不改（每个分支都有一条“照 TAS 走”的延续；从 A 出发的这一条就是零测试：必须给出 +0）；
- 概率 `--p-random`：前 `--window` 帧换成随机方向的保持（4–32 帧），一半偏向 TAS 当时的方向；
- 其余：在前 `--window` 帧开始的 run 上做 1+Poisson(`--mean-edits`) 次局部编辑：挪 run 边界（±2..24 帧）、方向转 45° / 90°、
  松键、用任一方向覆盖一段（2–32 帧）、删掉一个 run（邻居接过它的帧）。每种编辑都保持总长，后面的按键不动。

只用方向键（9 个动作：不按 + 8 个方向）；这两段 TAS 里没有转视角的键。

rollout 的停止：掉球 / Dead / GameOver / 通关、低于 TAS 本段最低点 15、过了最后一个门、在某个门比当时最好的分支晚
`--slack` 帧（默认 264）、`2.5 × gate_every + 200` 帧没过新门。

**约束。** 中途：分支过门 g 时，TAS 在门 g−1 之前吃到的分数球（ExtraPoint）和生命球（PreLifeUp）它也必须吃到，否则丢掉。
终点（`EndCheck`，B 处与 TAS 比）：速度 ≥ TAS − 0.5，水平朝向差 ≤ 20°，离 TAS 点 ≤ 3，高度 ≥ TAS − 0.5，球种相同，
这一段吃到的分数球 / 生命球不少于 TAS，没有掉球。分数（points）随时间变，不直接比，比吃到的事件。

**验证。** 通过终点检查的前 `--verify-top` 条：新进程、只用 TAS[:A] 作前缀、A→B 的按键 1 帧一块重放，搜索期间观测到的每个
位置（沿分支的整条链：父分支的样本 + 自己的样本）都必须逐位相同（`deterministic`），再用 1 帧轨迹重新算过 B 的帧和 SR。
报告的 Δ = 这条线 A→B 的 SR 毫秒 − TAS A→B 的 SR 毫秒（同引擎、同检测器、都是过 B 后的第一帧）。

**没做的：** 用当前策略（349 维检查点）做种子——要整套 BallanceEnv 特征，留作后续；这两段的 TAS 种子已经比 RL 快 2.7 s / 4–5 s。

## 回滚（进程快照，`ballrain/segsearch/procsnap.py`，2026-11-27）

Windows 引擎在进程里跑零售 2002 的 `physics_RT.dll`，BMMO 的 IVP 存档（只认 BMMO 自己的 IVP 结构）存不了它的状态。所以从进程**外面**做：
启动引擎的 Python 进程用自己的 `Popen` 句柄（只碰自己启动的进程，不按名字找），

- **存档**：等引擎所有线程都不跑（主线程停在等下一个动作的 recv 里），暂停全部线程，读出所有已提交、可写的私有页和映像页
  （不读映射视图、guard / noaccess 页），记下每个线程的 WOW64 寄存器上下文；
- **读档**：线程集合必须相同；整数 / 控制寄存器、x87 控制字、MXCSR 必须和存档时完全相同（不同就拒绝，进程不动；x87 / XMM 的数据寄存器
  在阻塞调用里是死值，只记数）；释放存档之后新分配的私有内存、取消多提交的页，把存下的页写回，恢复线程。

引擎不用改、不用重编（仍是 `bin-x86p2002f-pressure`），所以不用快照时输出自然和原来一样。Python 这边 `SnapSession`（`snapsession.py`）
连同 frames_done、tracker、帧日志、通道序号一起回滚。开销（这台 14700KF，引擎 46–47 MB）：存档 0.12–0.14 s，读档 0.10–0.13 s；
冷启动加前缀重放是 0.5–1.8 s。

**验收**（`python -m ballrain.segsearch.snapcheck F N KIND [LOADS]`；每项：存档后跑 2000 帧、读档再跑同样的按键，原始 OBS 字节逐位相同；
另起两个冷启动进程做前缀重放作对照）：

| 存档帧 | 后续按键 | 覆盖 | 读档后 vs 存档后 | 冷 vs 冷（屏蔽后） | 读档后 vs 冷（屏蔽后） |
|---|---|---|---|---|---|
| 1500 | 随机保持 | 普通行驶；再读档 500 次（每次接 40–400 帧别的按键）后重跑 | 相同（500 次后仍相同；句柄 150→150，私有内存 46.7→46.7 MB） | 相同 | 相同 |
| 4200 | TAS | 生命球（PreLifeUp 4415 → PostLifeUp 4573）、移动物体 | 相同 | 相同 | 相同 |
| 8600 | TAS | 分数小球跟随、收球、盘点 1 前后（9266 / 9276） | 相同 | 相同 | 相同 |
| 12200 | TAS | 小节 2 移动物体、生命球 | 相同 | 相同 | 相同 |
| 16000 | TAS | 小节 3 移动物体、分数球 | 相同 | 相同 | 相同 |
| 5240 | 进一号石变 | 变球全过程（Unphysicalize 5428 → 石球 6088） | 相同 | 相同 | 相同 |
| 5600 | 进一号石变 | 在变球动画中间存档 | 相同 | 相同 | 相同 |

两个冷启动进程之间本来就不同的只有三个字段，都是进程相关的值：MIND `ledge`（地址）、MIND `plane` 的 w（IVP 不维护的残值，§13 已列）、
SCOR `energy[4]`（参数格的指针）。屏蔽这三个字段后，冷 vs 冷、读档后 vs 冷都逐位相同。这条 TAS 整关不变球，所以变球用的是自己找的一串按键。
没测：暂停（TAS 里没有 Esc）、读档到另一个关卡 / 重生之后。

**限制**：进程外的状态不在快照里——放弃的分支里引擎写进文件的东西（`level.msg.inc`、日志）还在，Python 这边的 tracker 回滚了，但之后如果再读
level.msg.inc 可能读到放弃分支写的记录；引擎结束（通关、GameOver、帧数上限、STOP）之后不能再读档；读档要求引擎停在等动作的同一个位置
（寄存器不一致就拒绝）。测试：`tests/test_segsearch.py::test_engine_snapshot_save_load_identical`（`BALLRAIN_SEG_ENGINE_TEST=1`）。

## 结果（2026-11-27，headless，球序 ckid，这台 14700KF 上 7 个 worker）

总结：两段都**没有找到**比 TAS 快、终点又合格的线。这是“在下面这些尝试里没找到”，不是“不存在”；搜索只在 TAS 附近做
局部按键编辑（±2–24 帧的边界、45°/90° 转向、覆盖、随机保持），换路线、捷径不在它的范围里。数据（不作解释）：编辑过的
rollout 约三分之一掉下去（fell），一半以上因为落后被剪掉（behind）；小节4 的门 8、门 12–13 一轮只剩 1–2 个分支可展开。
合格线都和 TAS 同帧到 B（`result.json` 的 `keys_runs` = A→B 的按键）。

**正向对照（`runtime/segsearch/ctrl-idle20`）：** 把 TAS 在出生后插 20 帧不按键（之后的按键整体后移 20 帧），当作参考
重跑搜索（A 936 → B 2700，k 8+2，m 12，1 轮，672 次 rollout，628 引擎秒）。空 20 帧并不只是推迟：这条变差的 TAS
走了另一条路，到 B 时已经在往下掉（约 1925 帧后掉球）。搜索找到并冷启动验证了一条到同一个门早 359 帧（−1.356 s）的线，
也在往下掉。这说明这套流程能把一个大的领先一路带到 B 并验证出来；不说明它能找到小的、细的领先。

**开环说明：** 合格线在 B 的状态和 TAS 只差一点（例如小节4：速度 8.58 对 7.99，离 0.63），但 TAS 后面的按键是开环的：
从 B 接 TAS 帧 23300 以后的按键 1000 帧，三条合格线都没掉球，但最后离 TAS 线 38 个单位。接下一段要么照 TAS 原样（就是 TAS），
要么下一段也要搜（或者交给策略）。

### 单点改动扫描（`python -m ballrain.segsearch scan`，2026-11-27 22:30）

beam 搜索是随机抽样，不能说明“TAS 附近都试过”。扫描把 A→B 之间 TAS 按键的**每一处单点改动**都跑一遍，
其余按键照 TAS（开环），不剪“落后”：

- 挪边界：第 i 段和第 i+1 段的分界挪 d 帧，d = −24..+24（两段都至少留 1 帧）；
- 转方向：第 i 段转 −90 / −45 / +45 / +90 / 180 度；
- 松键：第 i 段松开方向键；
- 原来不按的段：换成 8 个方向之一。

| 段 | 按键段数 | 改动数 | 到 B 且吃够球 | 掉下去 | 引擎秒 | 最好的合格改动（冷启动验证） |
|---|---|---|---|---|---|---|
| 小节4 盘点 → 坡顶 | 35 | 1339 | 186 | 999 | 3324 | **−22.7 ms（−6 帧）** |
| 小节1 出生点 → 螺旋 | 41 | 1613 | 230 | 890 | 1461 | **−30.3 ms（−8 帧）** |
